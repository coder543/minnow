# RTX 3090 execution and measurements

Measured on an NVIDIA RTX 3090 (SM86, 24 GiB), Ryzen 9 7950X, and 64 GiB RAM,
with driver 580.173.02, CUDA 13.0, and Rust 1.98.1. The existing GPU power limit
was 420 W. These are LLaDA2.2-mini measurements; they do not describe GB10 speed.

## Execution paths

- INT4 and INT8 use BF16 tensor-core operands by default, with dequantization
  confined to registers. SM86 uses a shorter INT8 load pipeline for 16-row tiles.
- `--int8-expert-activations` selects W4A8/W8A8 on SM80 and newer. Activations
  are quantized once per projection input, shared across a fused gate/up pair.
  Integer tensor cores accumulate each group in INT32; FP32 scaled group sums
  produce BF16 projection output. The common 128-value group has specialized,
  prefetched kernels. This option changes numerical results.
- NVFP4 retains packed E2M1 weights, E4M3 block scales, and dynamic activation
  quantization. The SM80+ fallback uses BF16 tensor cores with exact block
  operands and applies the FP32 outer scales afterward. SM86 selects 32-row
  tiles for larger prefill batches and 16-row tiles for compact decode.
- SM120/121 keeps native FP4 instructions and its original tile defaults.
  The native NVFP4 PTX SHA256 is identical before and after these changes:
  `1f441c0a36f9f75e19cf3fe7da5e82e44785e31e0c9c8f62b009318c87931dbe`.
  Physical GB10 testing was unavailable for this change.

All paths keep one compressed resident weight copy per instance. Checkpoints
load directly into final allocations. Integer activation quantization is an
execution option, not a second checkpoint or expanded resident model.

## Controlled measurements

The release binaries were built before timing, with serving stopped. Settings:
BF16 dense layers, block FlashAttention, 4,096-token prefill chunks, 512 MiB
workspace cache, and default greedy diffusion settings. Integer weight groups
contain 128 values; NVFP4 groups contain 16.

The repeated comparisons use A/B/B/A order. Each target has ten timed prefill
samples, two sets of thirty cached forwards, and four generations per prompt
after warmup. Prefill excludes loading and the vocabulary head. Decode counts
text tokens, excluding special tokens, and excludes prefill time. Generation
prompts are the three cases in `tests/decode_natural_cases.json`, capped at 512
tokens for these measurements.

| Expert execution | 4,096-token prefill | Cached forward, 1,024-token prefix |
| --- | ---: | ---: |
| INT8 / BF16 activations | 13,094 tok/s | 8.714 ms |
| INT4 / INT8 activations | 15,667 tok/s | 7.316 ms |
| NVFP4 / BF16 tensor-core fallback | 11,578 tok/s | 12.218 ms |

| Prompt | INT8 / BF16 | INT4 / INT8 | NVFP4 |
| --- | ---: | ---: | ---: |
| What is the LHC? | 210 tok/s | 238 tok/s | 133 tok/s |
| React TypeScript example | 667 tok/s | 697 tok/s | 300 tok/s |
| Fellowship characters and backstories | 151 tok/s | 194 tok/s | 108 tok/s |

Different precisions produce different responses and stopping lengths. These
output rates include that effect. All repetitions within each execution mode
match their warmup tokens. The optimized NVFP4 kernels also reproduce the tokens
and refinement work of the validated BF16 fallback baseline.

A separate W8A8 run measured 15,473 tok/s at 4,096-token prefill (three samples)
and 8.772 ms per cached forward at a 1,024-token prefix (twenty forwards). Four
warmed generations per prompt produced 183, 622, and 159 text tok/s respectively
for LHC, React, and Fellowship. W8A8 improves prefill but has similar fixed-forward
decode latency to W8A16 on this GPU; output and refinement counts change.

INT8's default execution improves useful decode throughput by 12.5–14.3%
against commit `0197194c41625a4665be1f35003026ba349482c1`, with identical generated
tokens, stopping reasons, and refinement counters on all three prompts. Its
4,096-token prefill rate changes by less than 1%.

The INT4 comparison selects between BF16 and INT8 activations on the same packed
checkpoint. Its output tokens and refinement work differ, so output throughput
also reflects the changed decoding trajectory. Fixed cached-forward timing
measures equal numbers of refinement evaluations. A final 32-token block can
require many such evaluations.

Example comparison, after building and validating both binaries:

```sh
python3 scripts/memory_guard.py --report artifacts/comparison-memory.json \
  --max-growth-gib 8 --reserve-gib 16 --max-swap-mib 0 -- \
  python3 scripts/bench_cuda_arch.py \
    --a artifacts/minnow-baseline --b target/release/minnow \
    --model models/llada2.2-mini-int8.mnw \
    --input tests/prefill_benchmark_ids.json \
    --output artifacts/int8-comparison
```

Use the same binary for both targets and add `--b-int8-expert-activations` to
compare activation modes. The report records commands, binary/source hashes,
GPU clocks and temperature, individual timings, and generation/work equivalence.
Adjust host-memory budgets to the machine. Discrete GPU VRAM must also fit.

## Numerical and memory validation

The CPU suite covers INT4 codebook rounding, lossless fragment packing, direct
packed expert reads, and BF16 `.mnw` to INT4 conversion after removing the source
safetensors. CUDA oracles cover every group size, all four row tiles, uneven and
repeated experts, indexing, fused SiLU, and compact GPU routing. W4A8/W8A8 results
match independent scalar integer group dots exactly after BF16 rounding.

The Python oracle uses `scripts/layerwise_reference.py` and upstream model code,
holding one layer at a time. Strict whole-model BF16 parity remains unmet:
rounding differences propagate through attention and expert routing. On the
32-token arithmetic reference, logits RMS differences were 0.176 for INT8/BF16,
0.256 for INT4/BF16, 0.175 for INT8/INT8, 0.240 for INT4/INT8, and 0.306 for NVFP4.
Top-1 token agreement was 100% for the integer paths and 93.75% for NVFP4.
Kernel correctness and the three generation cases provide limited quality
coverage; broader task accuracy has not been measured.

Downloaded BF16, INT8, and NVFP4 containers and the generated INT4 container all
pass explicit checksum validation (14,813 tensors each). BF16-to-INT4 conversion
took 53.6 seconds and produced a 9.14 GiB file. The memory guard recorded less
than 2 GiB of additional host usage during conversion and no swap. Sequential
layerwise references peaked below 4 GiB of additional host usage, also with no
swap. The BF16 source remains read-only.

INT8 serving passed a 131,040-token prompt plus a completion with the full
131,072-token context exposed. Peak VRAM was 22,532 MiB, leaving 2,044 MiB free.
That prompt prefills at 4,251 tok/s; longer attention histories reduce throughput
relative to the 4,096-token measurements above. Five repeated 24,217-token
prompts with full cache allocation also passed, along with HTTP/SSE, tool-call
round trips, cancellation, and concurrent/late request admission. Full-context
K/V is 5 GiB shared across the instance's cache budget, independent of its
single resident weight copy.

With incremental K/V allocation, a functional INT8 concurrency check reached
four active requests and batches of four. Three uncapped responses plus a short
late request grew buffers from 2,048 to 10,240 tokens as needed. Peak aggregate
slot capacity was 24,576 tokens (960 MiB), with five growth operations and no
capacity errors. Cancellation released its slot in 51 ms. Full-model CUDA checks
preserved K/V and subsequent logits exactly across storage resizing and copying.
